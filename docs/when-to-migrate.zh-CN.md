# 什么时候该把手写 prompt 换成决策模型

把「让模型生成一段文本、再用字符串去解析」改造成「让模型在你的候选项上直接给概率，由代码取 argmax」。

这份文档回答两个问题：**哪些步骤值得改**，以及**怎么改才不出事**。

---

## 一、判定准则

三个条件**同时**满足才值得改：

| 条件 | 说明 | 反例 |
|---|---|---|
| ① 输出是**有限集合** | 候选可枚举，从几个到十几个 | 最终回答、开放文本改写 |
| ② 判断**依赖给定输入**而非世界知识 | 答案能从材料里推出来 | 需要外部事实、常识推理 |
| ③ 下游是**代码分支**而非给人看 | 结果用于 if / switch / 路由 | 摘要、话术、给用户看的文字 |

命中 ①②③ → 改造。只命中其一 → 保留生成，但可以用决策做**守卫**（第四节）。

一个常见的误判：**「模型现在能答对，所以它属于可改造」是错的。** 判定看的是输出的**形态**，不是当前准确率。反过来也成立——一个步骤现在靠 `strings.Contains(resp, "true")` 兜底、准确率不高，只要它满足 ①②③，改造成决策式通常同时提升准确率和稳定性。

## 二、接口

所有决策步骤走同一个接口，**不要为每个步骤单独造 API**：

```jsonc
POST /v1/decide
{
  "model": "doubao-2.1-lite",        // 可选；难步骤路由到更强底座
  "state": "<把原材料拼成的文本>",
  "questions": {
    "<步骤名>": { "type": "choice | noul | score", ... }
  },
  "debug": false
}
```

约定：

- **步骤名即 question key**，用小写下划线，与埋点字段同名，便于前后对比。
- 一次请求可放多道题。注意：模型对每道题是一次独立调用（服务内部并发），所以**多题 ≠ 单次前向**；响应里的 `calls` 会告诉你实际发了几次。
- 响应必带 `label` / `confidence` / `coverage` / `reliable` / `generated_token`。
- **候选数上限由 provider 决定**，不是固定 10：火山 20 个槽位可稳承载 10 个候选，百炼只有 5 个槽位所以上限 4，通用 OpenAI 兼容档保守取 8。超了直接 422。**先跑 `benchmarks/probe_provider.py` 测出你这家厂商的真实上限**，别照着文档猜。
- 模型侧固定、且**故意不做成配置项**：贪心（temperature=0）、`max_tokens=1`、只读答案位置的第一个 token。

## 三、三类改造模板

### A 类：有限候选项（分类 / 路由）

| 改造前 | 改造后 |
|---|---|
| prompt 要求输出数字或关键词 → 解析成整数 → 越界回退默认值 | `choice`，候选作为 `criteria` 传入，取 `label` |

```json
{"intent": {"type": "choice", "instructions": "用户这句话该走哪个能力",
  "criteria": {"billing": "账单、退款、支付问题", "technical": "故障、报错、功能异常",
               "account": "登录、权限、账号信息", "other": "以上都不是"}}}
```

**阈值策略**：`confidence < θ` 时不要硬取 argmax，走原来的兜底分支或路由到更强底座重跑。θ 用历史数据标定。

### B 类：是 / 否判断

| 改造前 | 改造后 |
|---|---|
| prompt 要求输出 True/False → 字符串匹配 | `noul`，取 `true_probability`，与阈值比较 |

```json
{"needs_retrieval": {"type": "noul", "instructions": "用户这句话是否在要求查资料 / 看文档？"}}
```

用 `decision`（≥0.5）还是阈值（如 ≥0.8），取决于业务对漏判和误判的容忍度——**必须在改造说明里写明取哪个**，否则后续维护者无法判断行为是否变化。

### C 类：有序打分

| 改造前 | 改造后 |
|---|---|
| 相关性靠规则打分（如 BM25） | `score` 对每个候选片段单独判档，取期望值排序 |

```json
{"doc_relevance": {"type": "score", "instructions": "这段资料与用户问题的相关程度",
  "scale": ["0","1","2","3","4","5"], "values": [0,1,2,3,4,5]}}
```

⚠️ **`score` 是本机制里准确率最低的一类**，实测和行业数据都是短板。用于排序可以，**不要用它做硬门槛**。

### D 类：必须生成

最终回答、话术、开放式改写、摘要等仍由生成模型完成。但它们不是只能原样留着——见第五节和第六节。

## 四、生成步骤的决策守卫

生成步骤不能决策化，但可以在关键处插决策守卫，把幻觉挡在出口：

| 守卫 | 题型 | 说明 |
|---|---|---|
| 引用核对 | `choice` | 回答里的每个事实点能否在召回材料中找到依据（SUPPORTS / REFUTES / NOT_ENOUGH） |
| 改写保护 | `noul` | 改写后的 query 是否引入了原句和材料里都没有的实体、型号、编码 |
| 答案合规 | `noul` | 回答是否越过了政策或口径边界 |
| 该不该反问 | `noul` | 当前是否应反问而不是作答 |

守卫失败 → **拒绝重生成或降级话术**，而不是让模型自己"再检查一遍"。

## 五、抽取优先：把「生成」拆成「选 + 拼」

第四节说生成步骤不改。但它们的目标（更快、效果不掉、无幻觉）依然可达，换一条方法论：

> **抽取优先（extractive-first）**：把「生成一段新文本」拆成「**选内容 + 拼装**」。
> 只要输出里的每个词都有出处——原文 span、封闭词表、模板槽位——就**不可能有幻觉**。
> 决策负责「选什么」，代码负责「拼起来」。只有当材料里确实没有可用内容时，才落回生成，且必须过守卫。

### 5.1 改写类

| 步骤 | 做法 | 题型 |
|---|---|---|
| ① 意图分类 | 判断这句话属于哪类改写 | `choice` |
| ② span 切分 | 代码切词（词典或现成 NER） | 代码 |
| ③ 逐 span 取舍 | 每个 span 判「保留 / 丢弃」 | `noul` |
| ④ 同义替换 | 替换项**只能从领域词典里选**，不允许造词 | `choice` |
| ⑤ 拼装 | 代码按模板拼接 | 代码 |
| ⑥ 兜底改写 | 仅当「词典无命中且必须改写」时才生成 | 生成 |
| ⑦ 守卫 | 结果是否引入了原句和材料里都不存在的实体 | `noul` |

收益：改写从 1~3s / 几百 token 降到约 0.4s / 1 token，且实体不可能凭空出现。

### 5.2 结构化抽取类

字段值不要留成自由文本——那等于把幻觉留在结构里：

| 字段类型 | 做法 |
|---|---|
| 类别 | `choice` |
| 实体、编码 | 有词典 → 代码命中；有歧义才让模型 `noul` 裁决 |
| 层级值（大类 / 小类） | 词典分两级：先 `choice` 选大类，再 `choice` 选具体项 |
| 融合（抽取结果 + 原文 → 检索式） | **不需要生成**，按固定模板拼装即可 |

### 5.3 摘要类

先分清要哪一种：

- **抽取式摘要（优先）**：对材料逐句做 `score`（这句该不该进摘要，0~5 档），过阈值就**原文照抄**拼起来。零幻觉（每句都是原文），且一次并发判 N 句比生成整段快。适用：要点汇总、多文档摘要。
- **生成式摘要（必须组织语言时）**：保留生成 + 三道闸
  1. **生成前**：只喂白名单材料，prompt 明确「只能使用下面材料」；
  2. **生成后**：逐句 `noul` 核对「这句话能否在材料里找到依据」，不合格的句子删掉或重写；
  3. **出口**：数字、型号、编码做字符串校验（见 5.4）。

### 5.4 去幻觉三件套（任何必须生成的场景通用）

| # | 手段 | 成本 |
|---|---|---|
| ① | **生成前约束输入**：白名单材料 + 禁止外部知识 | 0 |
| ② | **生成后逐句核验**：每句 `noul` 判「能否在材料中找到依据」 | 一次决策调用，可异步，不阻塞首字节 |
| ③ | **出口字符串校验**：数字 / 型号 / 编码必须能在材料里命中，否则拒绝 | **0 成本 0 延迟** |

第 ③ 条优先做：它挡得住绝大多数「看着很像但实际是编的」内容，且完全由代码完成。

### 5.5 不改质量的提速手段

| 手段 | 说明 |
|---|---|
| 前缀缓存 | system prompt 与固定材料前缀复用，长材料重复调用省掉重复 prefill |
| 结构化输出换长文本 | 决策 1 token vs 生成几百 token |
| 分级路由 | 简单样本走小档，难样本路由到强档（见第七节） |
| 流式 | 生成任务保持流式，用户感知延迟看首 token 时间 |
| 结果复用 | 同材料 + 相似输入的改写 / 摘要结果缓存 |

## 六、Prompt 模板标准

**关键差别**：生成式 prompt 教模型「怎么答」，决策式 prompt 只做两件事——把候选摆清楚、把输出钉死在第一个字符。

```
[输入]
<原材料，原样贴进来，不要在这里做总结>

[任务]
<一句话说明要判断什么>

[候选]
1. billing：支付、退款、账单相关
2. technical：故障、报错、功能异常

[输出要求]
只输出所选候选对应的编号（例如 1），不要输出任何其他内容。
答案编号（只输出一个字符，不要有任何其他内容）：
```

四条硬性要求：

1. **候选说明写清楚**。模型只靠描述区分候选，描述含糊会导致**系统性错分**——这是改造后最常见的失败原因，不是模型能力问题。
2. **静态内容放 system prompt**（角色约束 + few-shot），变化的材料放 user 消息，这样才能命中前缀缓存。
3. **绝不允许「先解释再回答」**。本机制只读第一个 token，任何前缀都会让判定失败。这条没有例外。
4. **候选超上限就拆题**，例如先判大类再判小类。拆题比引入第二条读出路径省得多。

## 七、选型与路由

基于 10 个底座的实测矩阵（见 [`benchmarks/REPORT.md`](../benchmarks/REPORT.md)）：

| 用途 | 依据 |
|---|---|
| 默认（大量轻量判断） | 性价比档：准确率贴平强档、延迟约为一半 |
| 难样本 / 需要多跳与数值推理 | 强档。实测 hard 档是各底座拉开差距的地方 |
| 事实核验类（SUPPORTS/REFUTES） | 不一定跟「强档」一致——**按任务族选，不要按模型大小选** |

两条经验：

- **不要默认用最强档**。瓶颈往往不在推理难度，而在别处（结构化输出稳定性、对某个档位的识别能力）。选型要做对照实验，不要凭直觉。
- **模型强 ≠ 适合本机制**。同一个厂商的大档不一定比小档更适合，因为噪声 token 的分布不同——实测有厂商越新的旗舰在每个槽位上混入的噪声越多，候选容量反而更小。

## 八、验收标准

每改一个步骤，必须过这五条：

| 维度 | 指标 | 通过线 |
|---|---|---|
| 效果 | 与现有生成式输出在**同一批真实样本**上的一致率 | 下游是分支判断：≥98%；带阈值的：错判率不超过现状 |
| 幻觉 | 输出落在候选集内的比例 | **100%**（不满足即报错、不计入统计——这是本机制与生成式的本质差别） |
| 耗时 | 单步 P50 / P95 | 相对「生成 + 字符串解析」，P95 至少降 50% |
| 稳定性 | 拒绝率（模型未按格式作答的比例） | ≤2%；超过就开 `logit_bias` 兜底或改 prompt |
| 成本 | 单步 token 数 | 不高于现状 |

**样本要求**：抽样必须**包含现在会走兜底分支的困难样本**——这类样本才是能否替换的关键。只抽简单样本会得到虚高的通过率，这是最容易自欺的地方。

## 九、检查单

- [ ] 候选集是否封闭，且不超过该 provider 的候选上限？超了就拆题
- [ ] 候选描述是否能让模型区分？拿 5 个真实边界样本自测
- [ ] prompt 是否已改成「只输出一个字符」的结构？
- [ ] 阈值 θ 是否用历史数据标定？取 `decision` 还是 `true_probability ≥ θ` 是否写明？
- [ ] 兜底策略：模型不按格式作答时走哪条分支？
- [ ] 路由选择：这步用小档够不够？是否要路由到强档？
- [ ] 样本集是否含困难样本？一致率是否达标？
- [ ] 埋点字段是否与现有指标对齐，便于前后对比？
- [ ] 灰度：先双跑记录、不影响线上，再切流量

## 十、边界：哪些不要试图改造

需要**创造语言**的场景——话术生成、品牌文案、多轮语气、复杂技术解释——本质就是生成。不要把它们决策化，接受其可能产生幻觉，用 5.4 的三道闸把其中的**事实**挡住即可。

判断口径：**下游是「给人看」的（条件 ③ 不成立），且内容无法从输入提取 → 保留生成。**
